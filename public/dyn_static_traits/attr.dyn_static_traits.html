#[dyn_static_traits]
Expand description

Generates a function-pointer table for a static trait.

The attribute is applied to a static trait and takes the name of the table to generate as its only argument, as in #[dyn_static_traits(DynClock)]. The trait is emitted unchanged, so it still works as a generic parameter, and the generated table adds runtime selection between its implementations. The generated code needs no runtime support and works in no_std crates.

§Static traits

In this crate, a static trait means a trait whose items are exclusively static associated methods, which Rust calls associated functions with no receiver in their signature. For example, fn page_size() -> usize is static, while fn page_size(&self) -> usize is not.

Static traits are useful as generic parameters for static dependency injection. A generic function such as fn read<T: Storage>() can call T::read() with the implementation selected at compile time. This pattern applies to many scenarios like allocators, logging, clocks, device access, synchronization policies, platform services, and other static interfaces.

Because their functions have no receiver, static traits are not dyn compatible, so a dyn Trait object cannot select their implementation at runtime. The generated table provides dynamic behavior for the same static interface instead. It is a concrete struct of function pointers, not a dyn Trait object. Each new::<T> call still names its implementation type statically, but the resulting table no longer carries T in its own type. Tables built from different implementations can therefore be stored behind one common type, passed across an API boundary, or chosen conditionally at runtime.

§Generated items

For #[dyn_static_traits(DynClock)] on a trait Clock, the macro emits the trait unchanged, followed by these items:

  • A struct DynClock with the visibility and generic parameters of Clock. It has one public field per associated function, named after the function.
  • An inherent pub fn new<T: Clock>() -> Self constructor that stores the functions of T in the fields. A function that T does not override uses the default body from the trait.
  • A Clone implementation that copies every function pointer. It places no Clone bound on the parameters of the trait.

The table, its fields, its constructor, and its Clone implementation receive generated doc comments. For a trait with one function, the expansion is roughly equivalent to the following code:

ⓘ
trait Clock {
    fn now() -> u64;
}

struct DynClock {
    pub now: fn() -> u64,
}

impl DynClock {
    pub fn new<T: Clock>() -> Self {
        Self { now: T::now }
    }
}

impl Clone for DynClock {
    fn clone(&self) -> Self {
        Self { now: self.now }
    }
}

§Function-pointer fields

Each field type keeps the parameters, return type, ABI, and unsafe qualifier of its function, so unsafe extern "C" fn read(pointer: *const u32) -> u32; produces a field of type unsafe extern "C" fn(pointer: *const u32) -> u32. Elided lifetimes in a signature become higher-ranked lifetimes of the function pointer, so a function such as fn first(text: &str) -> &str keeps its borrowing behavior. A field for an unsafe fn still requires an unsafe call and retains the safety contract of the original associated function.

A field is called with parentheses around the field access, such as (table.now)(), because table.now() would look for a method.

§Generic traits

Type, const, and lifetime parameters of the trait become parameters of the table, and new requires its implementation parameter to implement the trait with the same arguments, as in DynStore::<u8, 4>::new::<Zeros>(). A generic table is Clone regardless of its type arguments. Every type and lifetime parameter of the trait must appear in at least one function signature, because the generated struct would otherwise leave it unused.

The implementation parameter of new is named T when that name is free. When the trait itself or one of its type or const parameters is named T, the macro uses the first free name among TA to TZ, then TAA, TAB, and so on, so trait parameters can use any name.

§Requirements

The annotated trait must contain only static associated methods. The macro reports a compile error for:

  • functions with a self receiver,
  • functions with generic parameters, including lifetime parameters,
  • async or variadic functions,
  • associated constants, associated types, macro invocations, and other non-function items.

Functions may have default bodies. Some signatures pass these checks, but a function-pointer field cannot represent them, so the generated table fails to compile:

  • signatures that mention Self, which refers to the table inside the generated struct,
  • impl Trait in a parameter or return type,
  • parameter patterns other than plain names and _, such as mut value or (left, right), even in functions with default bodies.

Attributes on trait functions stay on the trait and are not copied to the fields. In particular, a function under a disabled #[cfg] still receives a field, so the constructor fails to compile.

§Examples

use dyn_static_traits::dyn_static_traits;

#[dyn_static_traits(DynClock)]
trait Clock {
    fn now() -> u64;
}

struct MonotonicClock;

impl Clock for MonotonicClock {
    fn now() -> u64 {
        42
    }
}

// Static dependency injection uses the trait as a generic parameter.
fn read_time<T: Clock>() -> u64 {
    T::now()
}
assert_eq!(read_time::<MonotonicClock>(), 42);

// Dynamic selection stores the generated function-pointer table.
let clock = DynClock::new::<MonotonicClock>();
assert_eq!((clock.now)(), 42);

Tables built from different implementations share one type, so a program can choose between them at runtime:

use dyn_static_traits::dyn_static_traits;

#[dyn_static_traits(DynConsole)]
trait Console {
    fn name() -> &'static str;
}

struct Serial;

impl Console for Serial {
    fn name() -> &'static str {
        "serial"
    }
}

struct Framebuffer;

impl Console for Framebuffer {
    fn name() -> &'static str {
        "framebuffer"
    }
}

fn select(graphics: bool) -> DynConsole {
    if graphics {
        DynConsole::new::<Framebuffer>()
    } else {
        DynConsole::new::<Serial>()
    }
}

assert_eq!((select(false).name)(), "serial");
assert_eq!((select(true).name)(), "framebuffer");

A generic trait produces a generic table, and default bodies fill the fields that an implementation does not override:

use dyn_static_traits::dyn_static_traits;

#[dyn_static_traits(DynStore)]
trait Store<V: Copy, const N: usize> {
    fn read(index: usize) -> V;

    fn capacity() -> usize {
        N
    }
}

struct Zeros;

impl Store<u8, 4> for Zeros {
    fn read(_index: usize) -> u8 {
        0
    }
}

let store = DynStore::<u8, 4>::new::<Zeros>();
assert_eq!((store.read)(2), 0);
assert_eq!((store.capacity)(), 4);

An unsafe associated function keeps its qualifier in the table:

use dyn_static_traits::dyn_static_traits;

#[dyn_static_traits(DynReader)]
trait Reader {
    /// Reads a value through a raw pointer.
    ///
    /// `pointer` must be valid for reads.
    unsafe fn read(pointer: *const u32) -> u32;
}

struct DirectReader;

impl Reader for DirectReader {
    unsafe fn read(pointer: *const u32) -> u32 {
        // SAFETY: The caller guarantees that `pointer` is valid for reads.
        unsafe { *pointer }
    }
}

let reader = DynReader::new::<DirectReader>();
let value = 7;
// SAFETY: `value` is live for the duration of the call.
assert_eq!(unsafe { (reader.read)(&raw const value) }, 7);
