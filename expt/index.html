Architecture-flexible multi-level page table management.

This crate builds and mutates page table hierarchies described by crate::meta::PageTableMeta and entries implementing crate::pte::GenericPTE. crate::pt::PageTable keeps the concrete representation available for compile-time dispatch, while the opaque module offers runtime selection among page table hierarchy formats.

Mutations are performed through crate::pt::PageTableCursor. See crate::pt::PageTableCursorLike for range expansion, partial failure, and cleanup behavior. crate::pt::cleanup::PendingCleanup groups pending TLB invalidations with the selected crate::pt::cleanup::TlbFlusher, which determines invalidation scope and completion guarantees. Callers can transfer pending cleanup out of a cursor to process it themselves.

Multi-level page table values deallocate all table frames in their page table hierarchies when dropped. Replacing a child-table descriptor deallocates its subtree’s table frames during the mutation, without waiting for pending TLB invalidations. Mapped data frames remain caller-managed. Callers must quiesce hardware users before dropping a multi-level page table. A mutable Rust borrow does not exclude hardware page walks.

§Access coordination

Page table mutation operations such as map and unmap do not coordinate software or hardware accesses during mutation. Before a mutation begins, the caller must ensure that all existing accesses to potentially affected virtual address ranges and to page tables at any level that may be modified or deallocated have completed. From the start of the mutation until both the operation has ended and crate::pt::cleanup::PendingCleanup has been correctly processed, software and hardware on all processors must not access those ranges or page table memory in any form, except as part of the mutation itself or the processing of pending cleanup.

This requirement covers software and hardware accesses on all processors and must be upheld by the caller in the system design. It is not expressed by marking each page table mutation method as unsafe. The caller is responsible for enforcing it at the boundaries where the page table hierarchy is put into hardware use and subsequent accesses are coordinated.

§Terminology

The terms multi-level page table and multi-level page table structure refer to the Rust abstraction representing translation across all levels, such as crate::pt::PageTable or crate::pt::DualPageTable, and to values of those types. A page table hierarchy is the corresponding in-memory data structure traversed by hardware. A single-root multi-level page table represents one hierarchy, while a dual-root value represents two independent hierarchies. A page table is one table at a single level within a hierarchy. Table frames, also called page table frames, are the physical frames storing those tables. One page table may occupy one or more table frames.

§Known issues

RISC-V mapping flags are not validated. Leaf permissions must include READ or EXECUTE, and WRITE requires READ. With debug assertions enabled, constructing a leaf without READ or EXECUTE panics. With debug assertions disabled, such an entry above level zero can be mistaken for a child-table descriptor. Traversal can then access mapped data as a page table and deallocate data frames as table frames. Callers must supply valid RISC-V leaf permissions until validation is implemented.
