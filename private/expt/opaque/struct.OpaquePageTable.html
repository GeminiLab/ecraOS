Expand description

A runtime type-erased multi-level page table.

The value stores root addresses and operations specialized for its concrete format. See table-frame lifetime and the safety requirements for page table updates.

Fields§

The physical root addresses of the managed hierarchies.

The variant matches the format selected by the originating descriptor.

§methods: PageTableMethods<A>

The operations specialized for the managed hierarchies.

The stored functions use the originating descriptor’s concrete format and allocator.

pub const fn dummy() -> Self

Creates a sentinel multi-level page table.

Allocation and mutation report bugs, while destruction is a no-op. The zero-root sentinel is suitable for constant initialization before replacement with a concrete value.

Source

pub fn root(&self) -> OpaquePageTableRoot

Returns the erased physical root addresses of the managed hierarchies.

The returned root is not translated or dereferenced by this accessor. Its table frames remain associated with this value, and copying the addresses does not extend their lifetime.

Source

pub fn leak(self) -> OpaquePageTableRoot

Consumes the multi-level page table without deallocating the table frames.

This operation reads only the stored root and calls none of the stored method pointers, including destruction. Another compatible allocator type can use the hierarchy, and the caller is otherwise responsible for arranging its deallocation.

pub fn map( &mut self, vaddr: A, paddr: PhysAddr, size: usize, flags: MappingFlags, ) -> PagingResult<A>

Maps a virtual address range to a physical address range.

The concrete page table hierarchy format comes from the originating descriptor. The range is rounded to base-page boundaries and existing mappings are replaced according to crate::pt::PageTableCursorLike::map. See Self::apply_actions for cleanup and partial-failure behavior.

pub fn unmap(&mut self, vaddr: A, size: usize) -> PagingResult<A>

Removes mappings from a virtual address range.

The range is rounded to base-page boundaries and mapped data frames remain caller-managed. See Self::apply_actions for cleanup and partial-failure behavior.

Source

pub fn apply_actions<I: IntoIterator<Item = PageTableAction<A>>>( &mut self, actions: I, ) -> PagingResult<A>

Applies a sequence of page table hierarchy actions.

The concrete page table hierarchy format comes from the originating descriptor. Each action is applied in order, including any immediate table-frame deallocation. Pending TLB invalidations are processed through the captured TlbFlusher before this method returns.

If an action fails, earlier actions remain applied and their pending TLB invalidations are flushed before the error is returned. An iterator panic also flushes completed mutations during unwinding while retaining the table frames in the remaining hierarchy. The operation is not transactional. See PendingCleanup for synchronization requirements and Self::apply_actions_with_cleanup for transferring cleanup on success.

Source

pub fn apply_actions_with_cleanup<I: IntoIterator<Item = PageTableAction<A>>>( &mut self, actions: I, ) -> PagingResult<A, PendingCleanup<A>>

Applies actions and returns pending cleanup on success.

Same mutation and partial-failure behavior as Self::apply_actions. Successful calls transfer cleanup without processing it. An action error or iterator panic instead causes the temporary cursor to process pending cleanup before returning the error or unwinding. The selected strategy and hardware-use preconditions must therefore permit automatic cleanup on these paths. See PendingCleanup for synchronization requirements.
