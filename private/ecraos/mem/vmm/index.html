Virtual memory management.

This module manages the kernel’s virtual address space layout and page table.

§Virtual address space layout

ecraOS currently uses a single shared virtual address space across all CPUs and tasks. Only the upper half of the virtual address space is used (after the temporary identity mappings are removed). It is divided into three areas:

AreaPortion of the upper halfPurpose
Direct mappingLower halfPhysical memory access.
VmallocNext quartervmalloc allocations.
ReservedFinal quarterNot used.

The kernel selects the virtual address space mode and calculates the layout during early boot.

§Direct mapping area

The direct mapping area provides access to physical memory at a fixed virtual address offset, returned by direct_mapping_offset. Adding this offset to a physical address gives its direct mapping address, provided the physical address fits in the area.

Use direct_mapping_phys_to_virt and direct_mapping_virt_to_phys to convert addresses within the direct mapping area once is_page_table_active returns true. These functions check address bounds, but do not look up page-table entries. A successful conversion does not guarantee that the resulting address is mapped.

§Physical region mappings

super::pmm maintains physical memory regions with byte-precise boundaries. Direct mappings round these regions outwards to base-page boundaries (the original physical memory regions table from super::pmm is not modified). Regions that share a page must satisfy the following rules:

  • Regions without any READ, WRITE, or EXECUTE bits are ignored unless marked NO_MAP.
  • A NO_MAP region excludes its entire rounded pages from mapping. A region marked KERNEL, BOOT_SERVICE, DEVICE, or EXECUTE must not share a page with a NO_MAP region.
  • Other mapped regions sharing a page must agree on their READ, WRITE, EXECUTE, DEVICE, and UNCACHED bits. Compatible regions share one mapping for each overlapping page.

Use add_and_map_phys_regions to add or overwrite physical regions and update their mappings. It also updates identity mappings while they remain active. Adding regions is expensive, so prefer adding them in batches.

§Vmalloc area

The vmalloc area is used for kernel allocations whose virtual addresses are chosen independently of their physical backing. Neighboring virtual pages can map non-contiguous physical pages. Use vmalloc to allocate and map memory in this area.

vmalloc_base and vmalloc_area describe the area reserved for these allocations. Querying this reservation does not allocate memory or guarantee that an address is mapped.

§Page table

The kernel page table defines the mappings and access permissions for the shared address space. Its format depends on the selected VirtAddrSpaceMode. Depending on the architecture, it may have a single root or separate roots for the lower and upper halves. All CPUs use the same kernel page table.

§Mapping transactions

Mapping transactions provide exclusive access to the VMM state, allowing page-table changes, TLB invalidation, and mapping record updates to be performed safely and serially.

Transactions do not roll back page-table changes if an operation fails. See the documentation for each method of MappingTransaction for details.

See add_and_map_phys_regions and the vmalloc interfaces for their calling requirements and failure behavior.

§Identity mapping

An identity mapping maps a virtual address to the physical address with the same numerical value. It allows startup code to execute before switching to the kernel’s upper-half addresses. Temporary identity mappings are needed by the bootstrap processor (BSP) during early boot and by application processors (APs) during secondary CPU startup. Identity mappings are removed after APs have finished early startup and no longer need them.

§Lifecycle of the virtual address space and page table

§When the kernel starts

The bootloader must provide a valid identity mapping for kernel entry, and that mapping must cover all physical addresses that the kernel will need to access before the early page table can be installed. The kernel initially executes through this mapping. Its own virtual address layout and page table have not yet been initialized. Both is_layout_initialized and is_page_table_active return false.

§Selection of the virtual address space mode

The platform reports supported virtual address space modes as VirtAddrSpaceMode values. A mode describes which halves are available, their address widths and page sizes, and whether they use separate page-table roots. The kernel currently selects its preferred mode as follows:

  1. Remove all modes that do not cover both halves of the virtual address space.
  2. Remove modes whose two halves have different address widths or base-page sizes.
  3. Choose the mode with the largest address width per half.
  4. If multiple modes remain, choose the one with the largest base-page size.

The platform then activates the selected mode and must ensure that a valid identity mapping remains available. It may preserve the existing identity mapping or install temporary page tables. The kernel then calculates its layout. The selected mode and layout remain unchanged throughout the rest of the kernel’s lifetime.

From this point, is_layout_initialized returns true and layout queries are available. is_page_table_active remains false, and both direct-map address conversion functions return None until the kernel page table is installed.

§Early page table

The kernel initializes its early page allocator and uses it to construct the early page table. Physical regions are mapped into the direct map according to the physical-region mapping rules, with low-address identity mappings. The kernel also allocates and maps a BSP stack in the vmalloc area.

Constructing this table does not activate it. Once the mappings are ready, the BSP installs the table, after which is_page_table_active returns true and direct-map address conversion is available in both directions. Execution then moves to the kernel’s direct-map code address and the new stack. The identity mappings remain available.

§Formal page table

After entering the upper half, the kernel initializes the buddy page allocator and the heap. The buddy allocator takes over allocation of frames already in use, including early page-table frames.

This begins the formal page-table phase. The existing page-table tree and its mappings are preserved. Runtime mapping transactions are now available, including updates through add_and_map_phys_regions. The vmalloc allocator is then initialized over its reserved area and records the existing BSP stack mapping. Identity mappings remain for AP startup.

§Removal of the identity mapping

Once APs have finished early startup and no longer need identity mappings, the kernel removes those mappings and completes the required local and remote TLB invalidation. Direct mappings and vmalloc mappings remain in place. Later physical-region updates maintain direct mappings without recreating identity mappings.
