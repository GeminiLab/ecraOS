Macro look_at

Generates wrappers and re-exports for declarations in an implementation module.

look_at! collects the public interface shared by several architecture-specific modules. The invocation names one implementation module, then lists declarations that should be available at the invocation site. The declarations are intentionally only signatures or placeholders: the implementation remains in the selected module.

§Overview

The target path is resolved once and is used for every item in the invocation. Functions are emitted as wrappers that call the target function. Types and use trees are re-exported, while constants are emitted as typed forwarding constants. The macro does not select the implementation module. A conditional import, such as the #[cfg] imports of current below, still selects it, and look_at! states and checks the interface that the selected module must provide.

mod x86_64 {
    pub fn halt() {}
    pub const PAGE_SIZE: usize = 4096;
}

mod riscv64 {
    pub fn halt() {}
    pub const PAGE_SIZE: usize = 4096;
}

#[cfg(target_arch = "x86_64")]
use x86_64 as current;
#[cfg(target_arch = "riscv64")]
use riscv64 as current;

look_at! {
    @current:
    pub fn halt();
    pub const PAGE_SIZE: usize;
}

The generated halt function calls x86_64::halt and PAGE_SIZE has the value from x86_64::PAGE_SIZE when building for x86_64, and their riscv64 counterparts when building for riscv64.

§Syntax

An invocation starts with @, followed by a Rust path and :. Every following declaration must end with ;. Attributes and visibility precede the declaration just as they do on ordinary Rust items.

ⓘ
look_at! {
    @crate::arch::current:
    #[cfg(feature = "debug")]
    pub fn initialize();
    pub type Context: Send;
    pub type Handle;
    pub const PAGE_SIZE: usize;
    pub use Error as InitError;
}

The invocation must contain at least one item. A function declaration has no body, and all other declarations are placeholders without a definition or value.

§Functions

Function declarations keep their name, visibility, generics, where clause, ABI, and const and unsafe qualifiers. Their parameter patterns are replaced with readable local names so the generated wrapper can forward each argument positionally. A single binding keeps its name, several bindings are joined with _and_, and a pattern without bindings becomes argument_N for its one-based position. A repeated name receives an _argument_N suffix. Wrappers are marked #[inline(always)].

ⓘ
look_at! {
    @crate::arch::current:
    pub fn copy_bytes<'a>(source: &'a [u8], destination: &mut [u8]);
    pub unsafe extern "C" fn enter(stack: *mut u8) -> !;
    pub fn combine<T>(left: T, right: T) -> T where T: Add<Output = T>;
}

Ordinary functions receive a generated function-pointer assignment that checks the declared signature against the selected target. Functions containing impl Trait in an input or output remain callable wrappers, but skip that generated function-pointer check because opaque types cannot appear in it. const functions also skip it, and their wrappers can only call const targets. The forwarding call still checks the arguments and the return value of these functions, but it permits coercions.

An unsafe wrapper calls its target in an unsafe block, so callers take on the safety requirements of the declaration. async functions, variadic functions, functions with a self receiver, and declarations with a body are rejected.

§Type declarations

A type declaration is a placeholder for a target type alias, struct, enum, or union. It emits a use re-export, so the target’s complete type definition and generic interface remain intact. Generic parameters are accepted to describe the intended interface, but are not independently checked or redeclared by the macro.

ⓘ
look_at! {
    @crate::arch::current:
    pub type Device;
    pub type Buffer<T>;
    pub type Context: Send + Sync;
}

A bound is allowed only on a non-generic placeholder. The macro checks it inside an anonymous constant, for example pub type Context: Send; verifies that the selected Context implements Send at compile time. Without a bound, the declaration only checks that the target type exists.

§Constants and use trees

A constant placeholder contains the name and expected type, but no value. The expansion reads the value from the selected module and assigns it to the declared type. A target constant of another type is rejected unless its value coerces to the declared type.

ⓘ
look_at! {
    @crate::arch::current:
    pub const MAX_CPUS: usize;
    pub use scheduler::Task as ArchTask;
}

A use declaration is resolved below the target path, so aliases and nested use trees can be forwarded without repeating the architecture path at each use site. It only checks that the named items exist.

§Compared with conditional re-exports

The conditional import in the overview example already keeps target selection in one place, so the selected items could also be re-exported directly:

#[cfg(target_arch = "x86_64")]
use x86_64 as current;
#[cfg(target_arch = "riscv64")]
use riscv64 as current;

pub use current::halt;

Both forms give callers one set of names without their own #[cfg] attributes, and both forward only the listed items. look_at! differs in how the interface is checked, which visibility its items can have, and what it generates. The remaining examples in this section define current directly and omit the #[cfg] selection.

§Interface checks

A re-export exposes whatever the selected module defines. When one implementation diverges from the intended interface, the crate that owns the interface still compiles. The mismatch surfaces only where a caller uses the item on that target, or not at all when nothing uses it. If the interface requires page_shift to return u32, this re-export of an implementation that returns u64 still compiles:

mod current {
    pub fn page_shift() -> u64 {
        12
    }
}

pub use current::page_shift;

look_at! checks each declaration against the selected module at the invocation site.

  • An ordinary function is assigned to a function pointer with the declared signature, so its parameter types, return type, and ABI must match exactly.
  • A constant is assigned to the declared type.
  • A type placeholder with bounds asserts that the target type implements them.

Declaring the same interface with look_at! rejects that implementation with a type mismatch:

ⓘ
mod current {
    pub fn page_shift() -> u64 {
        12
    }
}

look_at! {
    @current:
    pub fn page_shift() -> u32;
}

As with a re-export, a declaration also fails to compile when the selected module lacks the item. The checks cover only the module selected for the current build, so each implementation is checked when building for its own target.

§Visibility

A re-export cannot be more visible than its target, so pub use rejects a crate-private function:

ⓘ
mod current {
    pub(crate) fn halt() {}
}

pub use current::halt;

Function wrappers and forwarding constants are new items, and their targets only need to be accessible from the invocation site. An implementation module can therefore keep its items crate-private while the declarations form the public interface:

mod current {
    pub(crate) fn halt() {}
    pub(crate) const PAGE_SIZE: usize = 4096;
}

look_at! {
    @current:
    pub fn halt();
    pub const PAGE_SIZE: usize;
}

Type and use declarations expand to re-exports and follow the ordinary re-export rules.

§Costs

  • A function wrapper is a distinct function. Its address differs from the target’s, and attributes on the target, such as #[must_use] or #[track_caller], do not apply to the wrapper unless the declaration repeats them.
  • Each signature is written once more in the declaration and changes together with the implementations.
  • Some declarations are checked only partially. Type placeholders without bounds and use declarations only check that the item exists, and generic parameters on type placeholders are not checked. const functions and functions with impl Trait skip the function-pointer check and rely on the forwarding call, which permits coercions.
  • Some items cannot be declared, as listed in Unsupported items.

An attribute that callers of the wrapper should observe is therefore written on the declaration as well as on the implementation:

mod current {
    #[must_use]
    pub fn read_counter() -> u64 {
        0
    }
}

look_at! {
    @current:
    #[must_use]
    pub fn read_counter() -> u64;
}

A conditional re-export remains the simpler choice when callers need the target item itself, such as its function address or its attributes, when the items cannot be declared here, or when the interface needs no checks beyond those its callers already perform.

§Attributes and visibility

Outer attributes attached to an item, including doc comments, are copied to its generated wrapper, re-export, or constant. In particular, #[cfg(...)] can remove an item for architectures where it is unavailable. A bound check copies only the cfg and cfg_attr attributes of its declaration, so it is removed together with its re-export.

The visibility written in the invocation is used for the generated item and does not increase the visibility of the target definition itself. Function wrappers and constants may be more visible than their targets, while type and use re-exports may not, as described in Visibility.

§Documentation

Function wrappers and forwarding constants are new items, so their documentation consists only of the doc comments on the declaration. Type and use declarations expand to re-exports. When rustdoc inlines such a re-export, for example because the target module is private, it shows the doc comments on the declaration followed by those on the target item. That part of the page therefore depends on the target selected for the documentation build.

Doc comments on a declaration are shared by every implementation. They describe one interface regardless of the target, but they must hold for every architecture and cannot document the details of one implementation. A practical split is to describe the architecture-neutral contract on the declaration and to keep architecture-specific details on each implementation:

mod x86_64 {
    /// Returns 12 because x86-64 uses 4 KiB base pages.
    pub fn page_shift() -> u32 {
        12
    }
}

use x86_64 as current;

look_at! {
    @current:
    /// Returns the base-2 logarithm of the base page size.
    pub fn page_shift() -> u32;
}

The documentation of the generated page_shift contains only the declaration’s sentence, while the x86-64 detail stays with the implementation.

§Unsupported items

The current syntax supports functions, type placeholders, const placeholders, and use trees. Trait declarations, structs with inline fields, enum definitions, union definitions, and constants with values must remain in the selected implementation module and are not accepted as declarations here. Their definitions can still be forwarded with a type, const, or use declaration. Among functions, async functions, variadic functions, and functions with a self receiver are rejected, as described in Functions.
