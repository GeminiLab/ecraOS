Slab page layout and the operations performed on one slab.

This module is responsible for the in-slab side of allocation. It initializes slabs, tracks locally available slots in bitmaps, and receives slots released by other CPUs.

§Layout

A slab occupies SlabLayout::slab_size bytes and starts at an address aligned to that size. Byte ranges below are offsets from the slab base, C is the size-class slot size, and N is SlabLayout::slot_count.

Byte rangeContents
0..32SlabPageHeader
32..64Reserved summary bitmap
64..64 + ceil(N / 64) * 8First-level bitmap stored as u64 words
End of first-level bitmap through slot_offsetPadding for object alignment
slot_offset..slab_sizeN object slots, each C bytes and aligned to C

SlabLayout::slot_offset is the smallest byte offset after the bitmap that is a multiple of C. There is no trailing padding because the slot’s size and alignment is always a multiple of C.

§Bitmaps

Each bit in the first-level bitmap records whether its corresponding slot is locally available. A set bit means available. Bits beyond N remain clear. Allocation clears the bit of the slot it returns and local release sets it again, so a double-free triggers a debug assertion.

A slab with more than 512 slots uses the summary bitmap as a second level. One summary bit marks a group of 512 slots, and a set bit means the group has a locally available slot. Allocation locates a non-empty group through the summary and only scans the first-level bitmap of that group. For N <= 512 the region stays reserved and unused, and the first-level bitmap is scanned directly. The region is a fixed 32 bytes region after the header, so the maximum number of slots supported in a slab is 32 * 8 * 512 = 131072 which is far more than object_count’s limit and any slab actually needs.

Summary and first-level bitmaps are managed in 64-bit words.

§Remote releases

A slot released by another CPU is not recorded in the bitmap directly. The freeing CPU links it into SlabPageHeader::remote_free_head with a compare-and-exchange loop, and the owning cache later detaches whole batches and returns those slots to the bitmap. The header therefore carries two kinds of state: fields only the owner touches, and the atomic head that remote CPUs update. SlabPageHeader documents which is which.
