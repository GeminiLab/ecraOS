# maybe_non_generic Proc Macro Design

## Goal

Implement a `maybe_non_generic` attribute proc macro in a new crate with the
same name. The macro generates a function copy where selected const or type
generic parameters are replaced with ordinary runtime parameters. The first
consumer is `expt/src/lib.rs`, which already contains commented
`maybe_non_generic` attributes and a few hand-written dynamic-handler copies
that define the expected behavior.

The implementation must use Rust AST processing through `syn`, not token-level
string or stream rewriting.

## Current Context

The workspace currently has no `maybe_non_generic` crate. `dyn_static_traits`
is an existing small proc-macro crate using `syn`, `quote`, and
`proc-macro2`; `maybe_non_generic` should follow that style.

`expt/src/lib.rs` contains commented attributes for these copies:

```rust
#[maybe_non_generic(
    new_alloc_dyn,
    type(H => handler: DynPagingHandler),
    fn(Self::alloc_table => Self::alloc_table_dyn)
)]

#[maybe_non_generic(
    table_of_mut_non_const,
    const(LEVEL => level: usize)
)]
#[maybe_non_generic(
    table_of_mut_dyn,
    type(H => handler: DynPagingHandler)
)]
#[maybe_non_generic(
    table_of_mut_non_const_dyn,
    const(LEVEL => level: usize),
    type(H => handler: DynPagingHandler)
)]

#[maybe_non_generic(
    alloc_table_dyn,
    type(H => handler: DynPagingHandler)
)]

#[maybe_non_generic(
    clear_pte_dyn,
    type(H => handler: DynPagingHandler),
    fn(self.clear_pte => self.clear_pte_dyn),
    fn(PageTable::table_of_mut_non_const => PageTable::table_of_mut_non_const_dyn)
)]
```

`new_alloc_dyn`, `table_of_mut_non_const`, and `alloc_table_dyn` are currently
implemented by hand and should be deleted once the macro generates equivalent
copies. `table_of_mut_dyn`, `table_of_mut_non_const_dyn`, and `clear_pte_dyn`
should be generated by uncommenting the attributes.

`cargo check -p expt` currently passes. `cargo test -p expt` is currently
blocked by an unrelated test/API mismatch: tests call
`table.cursor::<TestPagingHandler>()` while `cursor` has no generic parameter.
That mismatch should be fixed after the macro work, as an additional task.

## Macro Argument Syntax

The attribute starts with a single output identifier. All following parameters
are comma-separated and order-independent.

Supported parameters:

```rust
const(PARAM => arg_name: arg_type)
type(T => arg_name: arg_type)
fn(fn_path => new_fn_path)
dont_copy_attr
attr(xxx)
```

Rules:

- The first parameter must be exactly one `Ident`; it names the generated
  function.
- Each `const(...)` parameter contains exactly one const generic replacement.
- Each `type(...)` parameter contains exactly one type generic replacement.
- Multiple replacements require multiple `const(...)` or `type(...)`
  parameters. A single grouped `const(A => a: usize, B => b: usize)` form is
  intentionally unsupported.
- `fn(...)` maps one call path to another call path. Multiple function-call
  mappings require multiple `fn(...)` parameters.
- `dont_copy_attr` is a bare identifier parameter.
- `attr(xxx)` adds `#[xxx]` to the generated function. The content `xxx` may be
  any legal Rust attribute body.
- Unknown parameter kinds, duplicate generic replacements, duplicate generated
  argument names, missing parentheses where required, or empty parameter bodies
  are compile errors.

The parsed internal model should be:

```text
output_name: Ident
replacements: Vec<Replacement>
fn_replacements: Vec<FnReplacement>
copy_attrs: bool
extra_attrs: Vec<Attribute>
```

`copy_attrs` defaults to `true` and becomes `false` when `dont_copy_attr` is
present.

## Accepted Targets

The macro accepts:

- free functions parsed as `syn::ItemFn`;
- inherent or trait implementation methods parsed as `syn::ImplItemFn`.

All other targets are compile errors. The function must have a body; unsupported
trait declarations, extern declarations, or semicolon-only methods are rejected
by target parsing or explicit validation.

The macro expands to the original function followed by the generated function.

## Signature Generation

The generated function preserves the original function's:

- visibility;
- receiver, if any;
- lifetime/type/const generics that are not replaced;
- `where` clause predicates that do not reference replaced generics;
- `async`, `unsafe`, ABI, variadic marker if supported by the target node;
- return type.

It changes the function name to the first macro argument and appends one
ordinary function parameter per replacement:

```rust
const(LEVEL => level: usize)
type(H => handler: DynPagingHandler)
```

append:

```rust
level: usize,
handler: DynPagingHandler,
```

in macro-argument order.

The replaced generic parameters are removed from the generated function's
generic parameter list. Bounds and defaults attached to removed generic
parameters are removed with them. `where` predicates that mention any replaced
generic parameter are removed as whole predicates. This is intentionally simple:
if a required constraint remains relevant, the caller should encode it in the
replacement argument type.

Replacing lifetime generics is unsupported.

If a replacement names a generic parameter that is absent from the target
function, expansion fails with a compile error.

## Function Body Transformation

The generated function body is transformed with a `syn::visit_mut::VisitMut`
AST visitor. The visitor maintains maps for const generic replacements, type
generic replacements, and function-call path replacements.

The design intentionally supports only the AST shapes required by the feature.
Unsupported uses of replaced generic parameters produce compile errors instead
of best-effort output.

### Type Parameter Static Access

For a type replacement such as:

```rust
type(H => handler: DynPagingHandler)
```

the macro supports direct static access expressions:

```rust
H::alloc_page_aligned(bytes_required)
H::phys_to_virt(paddr)
H::ASSOC_CONST
```

Function calls become function-pointer field calls:

```rust
(handler.alloc_page_aligned)(bytes_required)
(handler.phys_to_virt)(paddr)
```

Non-call associated item access becomes:

```rust
handler.ASSOC_CONST
```

This matches `DynPagingHandler`, whose fields are function pointers. More
complex forms such as `H::<...>::item` or `<H as Trait>::item` are unsupported
and should be compile errors.

### Const Parameter Expressions

For a const replacement such as:

```rust
const(LEVEL => level: usize)
```

the macro supports expression-position uses of the const parameter:

```rust
LEVEL
M::LEVEL_TABLE_SIZE[LEVEL]
LEVEL - 1
```

These become:

```rust
level
M::LEVEL_TABLE_SIZE[level]
level - 1
```

Const generic parameters left in type positions, array lengths, `where`
predicates, or non-call turbofish generic arguments are unsupported and should
produce compile errors.

### Function Call Path Replacement

For a function-call replacement:

```rust
fn(PageTable::table_of_mut_non_const => PageTable::table_of_mut_non_const_dyn)
```

matching ignores turbofish arguments and compares path segment identifiers.
The mapping applies to function calls whose callee is a path and to method
calls whose receiver plus method name match the left-hand side. Therefore this
call:

```rust
PageTable::<M, PTE>::table_of_mut_non_const::<H>(entry.paddr(), level - 1)
```

matches the rule. This recursive method call:

```rust
self.clear_pte::<H>(child, level - 1, child_vaddr)?
```

requires an explicit rule:

```rust
fn(self.clear_pte => self.clear_pte_dyn)
```

and becomes:

```rust
self.clear_pte_dyn(child, level - 1, child_vaddr, handler)?
```

The macro does not implicitly rewrite recursive or self-calls. If a generated
function body should call the generated function rather than the original, that
relationship must be expressed with `fn(...)`.

For path calls, the callee path is rewritten to the new path while preserving
compatible generic arguments from the original path. For method calls, the
receiver expression is preserved and the method identifier is replaced. Then
generic arguments that refer to replaced parameters are removed and converted
into ordinary call arguments appended to the call.

For example:

```rust
Self::alloc_table::<{ M::LEVELS - 1 }, H>()?
```

with:

```rust
type(H => handler: DynPagingHandler)
fn(Self::alloc_table => Self::alloc_table_dyn)
```

becomes:

```rust
Self::alloc_table_dyn::<{ M::LEVELS - 1 }>(handler)?
```

If multiple replaced generic arguments occur in one call, generated ordinary
arguments are appended in the order those generic arguments appeared in the
call.

### Generic Arguments In Calls

Any function call path with turbofish arguments may have replaced generic
arguments removed even when no function-call path mapping applies. The removed
generic arguments are appended as ordinary call arguments.

This supports forms such as:

```rust
table_of_mut::<LEVEL, H>(paddr)
```

becoming:

```rust
table_of_mut_non_const_dyn(paddr, level, handler)
```

when combined with a relevant call path mapping, or a same-path call with fewer
generic arguments when no path mapping exists.

If a replaced generic parameter appears in generic arguments outside a function
call, expansion fails.

### Error Collection

The visitor should collect `syn::Error` values with spans at the unsupported
AST node or generic argument. At expansion time, errors are combined and emitted
as `compile_error!` tokens.

After transformation, the generated body should be scanned for residual uses of
replaced generic parameters. Any residual use outside the explicitly supported
forms is a compile error.

## Attribute Handling

By default, the generated function copies all original function attributes,
including doc comments. Attributes whose path's last segment is
`maybe_non_generic` are filtered out, which prevents stacked macro attributes
from being copied onto generated functions and producing accidental recursive
copies.

If `dont_copy_attr` is present, no original attributes are copied.

Every `attr(xxx)` argument adds a generated-function attribute `#[xxx]`, even
when `dont_copy_attr` is present.

Attribute order on the generated function is:

1. copied original attributes, if enabled;
2. explicit `attr(...)` attributes in macro-argument order.

## Integration Plan

Implementation should:

- add `maybe_non_generic` as a workspace member;
- add a path dependency from `expt` to `maybe_non_generic`;
- import `maybe_non_generic::maybe_non_generic` in `expt/src/lib.rs`;
- replace the commented old semicolon syntax with the new comma syntax;
- remove hand-written `new_alloc_dyn`, `table_of_mut_non_const`, and
  `alloc_table_dyn`;
- let the macro generate `table_of_mut_dyn`, `table_of_mut_non_const_dyn`, and
  `clear_pte_dyn`;
- after macro integration passes, fix the existing test-only `cursor` API
  mismatch as a separate cleanup step.

## Verification

The main verification commands are:

```sh
cargo check -p maybe_non_generic
cargo test -p maybe_non_generic
cargo check -p expt
cargo test -p expt
```

`cargo test -p expt` should pass after the additional cursor test cleanup. If it
then exposes behavior failures unrelated to the macro, those failures should be
investigated separately and reported with concrete compiler or test output.

The macro crate should include focused tests for:

- parsing every supported argument kind;
- rejecting grouped `const(...)` or `type(...)` rules;
- signature generation with removed generics and appended runtime arguments;
- `H::function(...)` to `(handler.function)(...)`;
- const expression replacement;
- turbofish removal and argument appending;
- function-call path replacement that ignores turbofish while preserving
  remaining generics;
- `dont_copy_attr` and `attr(...)` behavior.

Compile-fail tests may be implemented with `trybuild` if the added dependency
is acceptable. Otherwise, parser and transformation unit tests plus `expt`
integration checks are sufficient for the first implementation.
