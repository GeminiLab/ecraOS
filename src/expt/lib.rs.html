1//! Architecture-flexible multi-level page table management.
2//!
3//! This crate builds and mutates page table hierarchies described by
4//! [`crate::meta::PageTableMeta`] and entries implementing [`crate::pte::GenericPTE`].
5//! [`crate::pt::PageTable`] keeps the concrete representation available for compile-time dispatch,
6//! while the [`opaque`] module offers runtime selection among page table hierarchy formats.
7//!
8//! Mutations are performed through [`crate::pt::PageTableCursor`]. See
9//! [`crate::pt::PageTableCursorLike`] for range expansion, partial failure, and cleanup behavior.
10//! [`crate::pt::cleanup::PendingCleanup`] groups pending TLB invalidations with the selected
11//! [`crate::pt::cleanup::TlbFlusher`], which determines invalidation scope and completion guarantees.
12//! Callers can transfer pending cleanup out of a cursor to process it themselves.
13//!
14//! Multi-level page table values deallocate all table frames in their page table hierarchies
15//! when dropped. Replacing a child-table descriptor deallocates its subtree's table frames during
16//! the mutation, without waiting for pending TLB invalidations. Mapped data frames remain
17//! caller-managed. Callers must quiesce hardware users before dropping a multi-level page table.
18//! A mutable Rust borrow does not exclude hardware page walks.
19//!
20//! # Access coordination
21//!
22//! Page table mutation operations such as `map` and `unmap` do not coordinate software or hardware
23//! accesses during mutation. Before a mutation begins, the caller must ensure that all existing
24//! accesses to potentially affected virtual address ranges and to page tables at any level that may
25//! be modified or deallocated have completed. From the start of the mutation until both the operation
26//! has ended and [`crate::pt::cleanup::PendingCleanup`] has been correctly processed, software and
27//! hardware on all processors must not access those ranges or page table memory in any form, except
28//! as part of the mutation itself or the processing of pending cleanup.
29//!
30//! This requirement covers software and hardware accesses on all processors and must be upheld by
31//! the caller in the system design. It is not expressed by marking each page table mutation method
32//! as `unsafe`. The caller is responsible for enforcing it at the boundaries where the page table
33//! hierarchy is put into hardware use and subsequent accesses are coordinated.
34//!
35//! # Terminology
36//!
37//! The terms **multi-level page table** and **multi-level page table structure** refer to the
38//! Rust abstraction representing translation across all levels, such as [`crate::pt::PageTable`]
39//! or [`crate::pt::DualPageTable`], and to values of those types. A **page table hierarchy** is the
40//! corresponding in-memory data structure traversed by hardware. A single-root multi-level
41//! page table represents one hierarchy, while a dual-root value represents two independent
42//! hierarchies. A **page table** is one table at a single level within a hierarchy.
43//! **Table frames**, also called **page table frames**, are the physical frames storing those
44//! tables. One page table may occupy one or more table frames.
45//!
46//! # Known issues
47//!
48//! RISC-V mapping flags are not validated. Leaf permissions must include `READ` or `EXECUTE`,
49//! and `WRITE` requires `READ`. With debug assertions enabled, constructing a leaf without
50//! `READ` or `EXECUTE` panics. With debug assertions disabled, such an entry above level zero can
51//! be mistaken for a child-table descriptor. Traversal can then access mapped data as a page
52//! table and deallocate data frames as table frames. Callers must supply valid RISC-V leaf
53//! permissions until validation is implemented.
